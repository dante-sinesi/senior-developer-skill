# Revisión completa del paquete senior (documento vivo)

Auditoría crítica de todas las partes del paquete: qué tan bien funciona cada una, dónde puede fallar y qué mejora más. Es la **base para seguir creciendo**: de acá salen las próximas tareas y acá se anota lo que se hizo. Las notas son un juicio (0 a 10) apoyado en mediciones hechas sobre el repositorio, no una métrica automática.

## Objetivo principal: que Token Diet se encargue del ahorro de tokens

`senior` no va a quedarse con las mecánicas de ahorro de tokens. Existe una skill nueva e independiente, **Token Diet** ([token-diet-skill](https://github.com/dante-sinesi/token-diet-skill)), dedicada únicamente a ahorrar tokens sin bajar el rendimiento de Claude. El objetivo principal es este:

- **Traspaso:** cuando una mecánica de Token Diet cubra lo mismo o más que la de `senior`, `senior` la suelta.
- **Dependencia:** desde ese momento `senior` pasa a depender de que Token Diet esté siempre instalada, porque sin ella consumiría demasiado. La dependencia va solo en ese sentido: Token Diet nunca depende de `senior`.
- **Criterio de traspaso (propuesta a confirmar):** una mecánica se traspasa cuando Token Diet tiene su equivalente con pruebas que muestren los mismos tokens ahorrados o más, sin bajar el éxito de la tarea.
- **Qué entra en juego:** las mecánicas inventariadas en el relevo (`docs/relevo-mecanicas.md` del repositorio de Token Diet): conversión de documentos e imágenes y su hook, auditoría de consumo (`consumo.py`, con `--repo`), la guía de salidas y lecturas, los resúmenes por script (`contexto.py`, `impacto.py`), el índice con los tokens de abrir cada resultado y los topes de texto.
- **Mientras tanto:** no se duplican esas mecánicas en Token Diet ni se agregan nuevas en `senior` sin consultar, para no tener dos hooks que bloqueen la misma lectura con instrucciones distintas.
- **Cuando se traspase:** `instalar.py` y `guardia_autoria.py asegurar` comprueban que Token Diet esté instalada y avisan si falta, y el punto ciego 17 se cierra.
- **Decisiones del 2026-11-13:**
  - **Dependencia excluyente.** Token Diet es el motor de `senior`: sin ella instalada y con la versión mínima, `senior` no se usa. Se comprueba en `instalar.py` (se niega a terminar), al abrir una sesión (primer paso de la skill, con `token_diet.py`) y en `asegurar` y `verificar` (fallan en lugar de avisar).
  - **Sin frenar sesiones sin supervisión.** Si falta la dependencia, `senior` no aplica su método y anota en `docs/pendientes.md` el comando de instalación, sin preguntar ni esperar; la sesión sigue con lo que no necesite `senior`. Instalar Token Diet requiere la aprobación del usuario porque modifica `settings.json`.
  - **Orden.** El bloqueo duro se activa solo en el último paso (3.7), con Token Diet ya instalada y verificada; antes, `senior` quedaría inutilizable.
  - **Alcance.** También se traspasan el índice de la memoria y la ceremonia proporcional. No se mueven los guardias de seguridad (autoría, escritura fuera del proyecto, archivos protegidos, secretos): al retirar el modo de hooks y el hook en un solo proceso hay que separar lo que es consumo de lo que es protección.

## Cómo se mantiene

Cada Pull Request que toque una parte puntuada o un punto ciego actualiza este documento **en el mismo PR**:

1. **Puntaje por parte:** cambia «Nota hoy» solo si hay evidencia (una prueba, una medición o un uso real), y ajusta «Mejora propuesta» (lo hecho se tacha con ~~esto~~ y se deja lo que falta).
2. **Puntos ciegos:** cambia el estado (**Abierto**, **En curso**, **Parcial**, **Resuelto**) y anota la rama o el PR. Un punto ciego nuevo que aparezca se agrega con el número siguiente.
3. **Historial:** una fila por cambio, con fecha, PR y las notas que se movieron.
4. **Promedio global:** se recalcula con las filas de la tabla.

Si una nota baja (algo se rompió o se descubrió un problema), se anota igual: el documento sirve si es honesto.

## Cómo se midió

- **Inventario:** 131 archivos versionados al inicio, 16 skills y unas 10.900 líneas de Python. La skill `senior` es la más grande (18 scripts, ~5.000 tokens al activarse) y `senior-diseno` la segunda (9 scripts, 12 referencias).
- **Hooks:** 28 formas de escribir fuera del proyecto (y de solo leer) contra el hook real. Al inicio **6 se le escapaban**; ahora se frenan todas y `tests/probar_hook_fuera.py` las vigila. Cada hook tarda unos 180 ms y una llamada de Bash o Write pasa por 3 a 5 (de ~0,55 s a ~0,9 s). Con el despachador del punto 7, una llamada de Bash pasó de ~400 ms (cuatro hooks sueltos) a ~150 ms.
- **Documentación inferida:** `/documentar-proyecto` se corrió sobre código Python real (este repositorio, copiado a `.temporal/`). Encontró módulos y variables de entorno, pero 2 de las 6 primeras «reglas de negocio» eran falsos positivos (un docstring y una expresión regular); ya no salen.
- **Compatibilidad:** el README prometía Python 3.8, pero 15 scripts usaban `Path.write_text(newline=…)` (3.10+) y un hook usaba `str.removesuffix` (3.9). El CI de GitHub lo mostró en el primer intento. En una versión vieja el hook se rompía y, como un hook que falla no bloquea, dejaba de proteger sin avisar. El mínimo documentado es **Python 3.10**.
- **Secretos:** la batería `tests/probar_secretos.py` arma claves falsas al vuelo y comprueba el detector, `.env` con y sin permiso, los hooks de git sobre un repositorio y un remoto de prueba y 27 casos del hook de Claude.
