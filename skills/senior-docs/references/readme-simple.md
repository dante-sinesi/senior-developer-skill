# README simple: para quien llega por primera vez

Un buen README se entiende sin saber nada del proyecto, ni siquiera programar mucho. Explica la **idea** y deja el detalle técnico un clic más abajo, en `docs/`. Lo hacen así los repositorios que se leen con gusto, y lo importante es que lo pueda leer también quien no domina el idioma o el tema.

## El orden

1. **Qué es:** una o dos frases, y el problema que resuelve.
2. **Qué te da:** tres o cuatro ideas, una frase cada una.
3. **Cómo funciona:** diagramas y tarjetas, con una frase debajo. Mostrar en lugar de explicar.
4. **Cómo empezar:** tres pasos como máximo, con el comando exacto.
5. **Más información:** enlaces a la documentación técnica.
6. **Para quien colabora:** al final, lo técnico: requisitos, estructura de carpetas y pruebas.

## Cómo se escribe

- **Un párrafo, una idea,** de una a tres frases. Frases de unas veinte palabras como mucho.
- **Palabras de todos los días.** Un término técnico solo si no hay otro, y explicado la primera vez.
- **Lo abstracto primero:** qué hace y para quién, antes de cómo. Nada de rutas, nombres de archivo ni opciones de comandos en la parte de arriba.
- **Verbos concretos** («revisa», «recuerda») y no sustantivos largos («realiza la revisión de»).
- **Cifras solo si están medidas,** con su origen. Una cifra sin origen no se pone.
- **Los detalles no se borran:** pasan a `docs/` y el README los enlaza.

## Ejemplo

Antes: «`senior` es la puerta de entrada: reparte el trabajo entre las skills del método, del relevamiento, del diseño y los comandos, todas sobre el mismo proyecto.»

Después: «Le pides algo a `senior` y él reparte el trabajo.»

## Cómo se comprueba

Los números ayudan (frases largas, mucho código o nombres de archivo en las primeras líneas) pero no alcanzan: la medida válida es que lo lea una persona que no conoce el proyecto y diga si lo entendió. Cuando hay dudas, se comparan dos versiones a ciegas y elige quien lee.
